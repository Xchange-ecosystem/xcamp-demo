### CFM-05 — What do the live agreement/settlement RPCs actually cover?

**Tag: CONFIRMED** (all 6 exist and are current) — **with a significant GAP flagged**

All 6 functions are defined, current, and unmodified since `supabase/migrations/20260604000002_objective_lifecycle_rpcs.sql` (checked all later migrations — none touch them). Reconstructed state machine:

```
sketch/inactive → promote_objective_to_agreement (owner) → active (contract created, value locked)
active → accept_objective_agreement (each assignee) → assignment accepted
active (≥1 accepted) → initiate_objective_completion (owner) → confirming (round-based confirmation records created)
confirming → record_completion_decision('confirmed', all participants) → _finalize_objective('unanimous') → completed (rewards/wallet settled)
confirming → record_completion_decision('dissented', any participant) → disputed (terminal — no resume path exists)
confirming (deadline passed, no real dissent) → owner_close_with_dissent (owner) → _finalize_objective('owner_override') → completed
```

Notable findings: `owner_close_with_dissent` is misleadingly named — it explicitly **refuses to run if a real dissent exists**; it's a timeout override for silence, not an actual dissent-handling path. `disputed` is terminal within this migration — no RPC resolves it. Settlement (wallet ledger, reward issuance) only happens inside `_finalize_objective`.

**GAP:** searched all of xcamp-backend's `src/routes`, controllers, and services for calls to any of these 6 RPC names — **zero matches**. `src/routes/objectives.routes.ts` only exposes `create-from-brief`/`suggest-tasks`/`suggest-collaborators`/`generate-dynamix-suggestions` — no agreement/completion/dissent endpoints exist. This entire state machine appears to be **defined in SQL only and not wired into the backend API**. `BLOCKED`: could not verify whether a frontend calls these directly via the Supabase client/PostgREST (outside this session's backend-only scope) — that would change this from "orphaned" to "called elsewhere."

### CFM-06 — What does `@xchange/ui` / xcamp-sdk actually export and cover?

**Tag: DIVERGES** (significant — flagged as the top design-system finding)

**`@xchange/ui` (xcamp-designsystem, v0.2.1)** exports, per `src/index.ts`: `App` (unmodified Vite scaffold placeholder, not a real component), `skin/*` (theming/token system: tones, gravity tokens, persona display metadata, `applySkin()`), `ai/*` (type-only contracts), `tokens/layout|spacing|shadows`, and `claude-design/*` (re-exported Figma/Claude Design token JSON). **There are no traditional UI components** — no Button, Card, Input, Modal, Table, Nav, Toast, etc., despite the package name. `src/backcasting/` exists as source but is dead/unexported code. Two unresolved design conflicts are tracked in `CONFLICTS.md` (font mismatch, dark-theme brand color). No Storybook.

**xcamp-sdk** is a pnpm monorepo with 3 packages (not 2 — `@xchange/generation` exists beyond the briefing's listed `@xchange/client`/`@xchange/companion`):

- `@xchange/client` (v0.1.0): API/data layer — Vox conversational client, Supabase wrapper, conversation store, and REST wrappers for objectives/Dynamix-AI/Chi-metrics/correlate/search endpoints.
- `@xchange/companion` (v0.1.0): **this is where the real UI components actually live** — `CompanionCardStack` and `ChiCompanionPanel`. It depends on `@xchange/ui` via a separate GitHub dependency (not a workspace link) purely for styling tokens.
- `@xchange/generation` (v0.1.0, newest, added 2026-08-06): pluggable LLM-generation abstraction (`GenerationPort`, `ChiAiAdapter`, `DirectLlmAdapter` — same adapters referenced in GAP-08 above).

**Key discrepancy to flag explicitly:** the project CLAUDE.md rule "All UI must use xcamp-designsystem exclusively" is **not enforceable as written** — xcamp-designsystem has no components to use. The actual reusable UI components live in `@xchange/companion` (xcamp-sdk), which itself only pulls xcamp-designsystem in for tokens. This matches what xcamp-companion actually did (skip `@xchange/ui`, use shadcn instead) — the app's divergence from the design-system mandate looks less like non-compliance and more like the design-system package genuinely not offering anything to comply with yet.

## What This Changes About the P1 Plan

1. **`@xchange/ui` P1.0 task needs re-scoping, not just "install it."** The package has no components — only tokens. Before any P1 screen can "use `@xchange/ui`" per CLAUDE.md, either (a) real components need to be built into xcamp-designsystem, or (b) the plan should explicitly route UI through `@xchange/companion` (which already has real components: `CompanionCardStack`, `ChiCompanionPanel`) and treat `@xchange/ui` as tokens-only. Recommend flagging this to Fabian/Pascal as a blocking decision before more P1 screens get built against shadcn (which is what's happening today and creates more design-system debt).

2. **Card Feed and mock-data-layer P1.0 tasks are genuinely not started** — no shortcuts here, budget real time for both. `GoalsFeed.tsx` is a reasonable extraction candidate for Card Feed if the team wants to generalize existing work rather than build from scratch.

3. **Routing/scaffold and deployment-pipeline P1.0 tasks can likely be trimmed or marked done-with-caveats** — TanStack Router is live with a wide route set, and Vercel deployment is confirmed live in production. The only real gap there is CI (no GitHub Actions) and confirming which 5 routes map to "the P1 screens" against the ClickUp WBS.

4. **The Navigator vs. Logbook question for the collaborator feed has a clear answer** (Navigator) — CFM-02 can inform P1.0/P1.x session prompts directly instead of requiring further design discussion.

5. **CFM-05's RPC-orphan finding is a potential scope surprise for any P1 work assuming the agreement/settlement flow is live end-to-end** — it is not reachable via the backend API today. If P1 screens are meant to let users promote objectives to agreements or confirm completions, that requires either new backend routes or confirmation that a different client already calls these RPCs directly.

6. **Security shadow-mode flip (GAP-01/02/09) is not a P1 UI task but should be raised as a fast, high-leverage fix** — flipping `AUTH_SHADOW_MODE=false` in both `.do/app.yaml` configs (after confirming shadow logs are clean) closes 3 of 5 open gaps with no code changes.

7. **GAP-08 (OpenAI bypass) is unrelated to P1 screen work but is a real, still-open architectural debt item** (~20+ direct-OpenAI call sites) — worth its own ticket rather than blocking P1.
