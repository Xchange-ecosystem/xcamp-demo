# Route & Screen Inventory Audit — P2a Epic 1

**Date:** 2026-09-13
**Type:** Phase 0 audit only. Read-only against the repo as it stands (both the functional route tree and the `/demo/*` route tree live in this repo already — no cross-repo duplication was needed). No application code was changed. This file is the only artifact this session produced.
**Repo:** `Xchange-ecosystem/xcamp-demo`, branch `claude/wonderful-johnson-d8vmlf`.
**Gates:** This document is what Epic 3 (hook extraction) and Epic 4 (screen wiring) are gated on. No code changes should start against those epics until this lands.

**Method:** Every route file under `src/routes/` was read directly (TanStack Router file-based routing — flat dot-segment filenames, e.g. `demo.founder.dashboard.tsx` → `/demo/founder/dashboard`; `src/routeTree.gen.ts` is gitignored/generated and was not regenerated, consistent with prior in-repo audits' standing rule). Every component/hook a route imports was traced for its actual data source (fixture import vs. `supabase`/`*-api.ts` import), not inferred from naming. A local dev server (`bun run dev`, Vite, port 5183) was started with a copied `.env.example` (no real Supabase anon key available in this sandbox — `.env` was never committed, confirmed gitignored) and driven with Playwright/Chromium to capture actual network activity for a representative sample of screens — see §4. Three background research agents did the exhaustive per-screen source tracing for the Founder, Investor, and Collaborator persona trees in parallel; their evidence (file:line citations, grep output) is folded into §5's table and cross-checked against direct reads of the shell/auth/context layer done in this main session.

Three prior in-repo audits (`docs/audits/microapps-inventory-2026-09-08.md`, `docs/audits/investor-operator-showcase-phase0-2026-09-12.md`, `docs/audits/xcamp-companion-briefing-01-2026-09-09.md`) were used as background and cross-checked against current source — the demo route tree has grown substantially since the oldest of those (5 days prior): Founder gained a 4-view Navigator (Board/List/Network/Timeline) and 6 MicroApps; Investor gained a full project-scoped sub-tree (Home/Dashboard/Pitch/Readiness) and an Ecosystem Navigator; Pitch and Readiness went from "Absent" to fully built (fixture-only) screens. Where this doc's findings supersede those older audits, it says so explicitly.

## 1. Auth, tenant, and shell architecture — confirmed once, applies to every demo row below

**Real auth gate:** `src/components/AppShell.tsx:200,256-258` — `const { user, loading } = useAuth(); ... useEffect(() => { if (!loading && !user) navigate({ to: "/auth" }); }, ...)`. This wraps every functional (non-demo) route: `/home`, `/navigator`, `/journal`, `/notes`, `/profile*`, `/project/*`, `/project-builder`, `/project-details`, `/portfolio`, `/ecosystem-navigator`, `/ecosystem-dashboard`, `/ai-plan`, `/admin/recap`, `/task/$taskId`, both `/sandbox/*` routes.

**Runtime-confirmed** (Playwright, this session): loading `/navigator`, `/portfolio`, and `/ecosystem-navigator` unauthenticated redirects to `/auth` every time — the gate works as designed at runtime, not just in source.

**Real tenant context:** `src/contexts/auth.tsx:20-30` — `buildXcampUser()` calls `resolveCentralUser(authUserId)` (`src/lib/xcamp-api.ts`) and sets `tenantId: cu.tenant_id` from the resolved central-user row. Downstream real queries scope by this, e.g. `src/lib/xcamp-api.ts:643-658`'s `collaborators` table query: `.eq("tenant_id", user.tenantId)`.

**Demo bypass:** `src/components/demo/DemoShell.tsx` (full file read) imports zero auth/tenant context — no `useAuth`, no `useActiveProject`. Confirmed by repo-wide grep across `src/routes/demo*.tsx`, `src/components/demo/`, `src/components/founder/`, `src/components/investor/`, `src/features/investor-portfolio/`, `src/features/investor-project/`, `src/features/collaborator/`: **zero** `useAuth` hits, **zero** `supabase`/`xcamp-api` import hits. This is a deliberate design choice, not an oversight — `DemoShell`'s own header comment (`DemoShell.tsx:20` per its creation commit `fbe86b3`) states it exists specifically to drop `AppShell`'s auth redirect, which had been incorrectly gating `/demo/*`.

**Tenant/workspace in the demo layer: absent, not faked.** No fixture file (`src/fixtures/*.ts`) and no demo component prop anywhere carries a `tenant_id`/`workspace_id` field — confirmed by grep across the entire fixtures directory and all three persona trees. This is not a hardcoded fake tenant; the concept doesn't exist at all in the demo data model. The one exception worth naming: `InvestorEcosystemProvider` (`src/contexts/investor-ecosystem.tsx:17-27`) manages a `sessionStorage`-backed `ecosystemId`, and its own header comment explicitly documents why it is *not* wired to anything tenant-like: "Deliberately its own sessionStorage key, not the real app's `ActiveProjectProvider`... conflating the two would let switching ecosystems in this fixture-only demo silently change what the real, authenticated app's sidebar has active." This is a case of the demo code proactively avoiding entanglement with the real tenant model, which is worth preserving as a design principle when Epic 3/4 build the real thing.

**Runtime-confirmed:** on every sampled `/demo/*` route, the *only* network requests observed were Google Fonts CSS. One inert, screen-independent Supabase call does fire on every route (demo included): the root-level `AuthProvider` (`src/routes/__root.tsx:111`, wraps the entire app regardless of route) calls `supabase.auth.getSession()` unconditionally on mount (`src/contexts/auth.tsx`, effect with `[]` deps). In this sandbox (no real `VITE_SUPABASE_ANON_KEY`), that single call fails against a `.invalid` placeholder host and surfaces as a console `ERR_CONNECTION_RESET` + a `[Supabase] Missing environment variable(s)` warning — visible in the console log on every route, demo or functional. This is global chrome-level session bootstrapping, not a screen fetching its own data, and it does not affect what a demo screen renders (its `user` value is simply never read by `DemoShell`). Flagging so nobody mistakes that console noise for a demo screen "actually calling Supabase."

## 3. Legacy / superseded code — cross-checked against the known gap list

- **GAP-01 (xcamp-backend JWT decode without signature verification) / GAP-02 (zero inbound auth on chi-orchestration `/api/*` and `/sync/*`):** Neither gap lives in this repo — both are backend repos (`xcamp-backend`, `chi-orchestration`) outside `xcamp-demo`'s scope, and per `P0CrossRepoAuditReport.md` (2026-09-03, in-repo) both are now "PARTIALLY RESOLVED" upstream (real JWKS verification exists but is fail-open behind `AUTH_SHADOW_MODE`, default `true` in production). **Relevance to this audit:** confirmed by direct grep, `xcamp-demo` itself calls exactly one of those backends' real endpoints from any reachable functional route: `src/lib/backcaster-api.ts` (`/project-builder`, `BASE_URL = "https://xcampapi.xchange.eco/api/v1/backcaster"`), plus `src/lib/organiser-api.ts`, `transcripts-api.ts`, `useVox.ts`/`vox/client.ts` (all hitting the same `xcampapi.xchange.eco` host — confirmed by `docs/audits/xcamp-companion-briefing-01-2026-09-09.md` to be an alias for `xcamp-backend`, not the separate `vox7` service the gap list's naming might suggest). **Do not treat "the functional route calls the real backend" as inherently safe wiring to port forward as-is** — that backend's auth is documented, in-repo, as still fail-open in production today. When Epic 3/4 extract these functional routes' hooks for reuse in `/demo/*` screens (Project Builder, Organiser, Transcript extraction), note that "real" here means "real but sitting behind a known-fail-open auth boundary," not "known-secure." No code change needed in `xcamp-demo` itself for this — it's a fact to carry forward, not a defect in this repo.
- **Chi-organiser client bug carried in vendored code, not reachable from `/demo/*`:** `vendor/client/src/proposals/executeProposal.ts:34` calls `xcamp-backend`'s `/api/proposals/execute` — but per `docs/audits/xcamp-companion-briefing-01-2026-09-09.md`, this is only reachable through `ChiCompanionPanel.tsx`, which no file in `src/` imports (confirmed dead in `xcamp-demo`), and independently broken even if it were reachable (`executeProposal(card.proposal, getSessionToken, "")` — an empty-string `backendUrl` that always falls through to a Supabase RPC fallback, never hitting the intended route). Flag: do not resurrect `ChiCompanionPanel.tsx` or wire it into any demo screen without fixing this bug first.
- **Retired Scientific/Playful skin axis:** confirmed retired — `src/styles.css:122,169` states directly "single unified skin — the Scientific/Playful axis [is retired]." The axis still exists as dead weight in `vendor/ui/src/skin/{tokens,types}.ts` and `vendor/ui/src/claude-design/tokens.ts`, but **confirmed not reintroduced anywhere live**: the only two references to `vendor/ui`/`@xchange/ui` inside `src/` are `src/main.tsx` (a comment) and `src/types/modules.d.ts` (a bare `declare module "@xchange/ui/styles"` for a CSS side-effect import type, not runtime skin logic). No functional or demo route imports skin tokens from the vendored package. One narrow exception, **not a live reintroduction**: `src/routes/sandbox.task-panel-live.tsx` and `sandbox.task-panel-v3.tsx` hardcode literal color/radius values copied from a *different* repo's (`xcamp-foundation`) "scientific" skin, explicitly to reproduce that other repo's real production surface for side-by-side comparison — self-labeled "THROWAWAY SANDBOX — not a real app surface, not linked from any nav." Flag for awareness, not action: if these sandbox routes are ever promoted or copied from, strip the hardcoded xcamp-foundation tokens rather than carrying them into the design system.
- **`chiDispatch()` / `handleAiProxy`-style stubs:** grepped repo-wide, zero hits under either name. No dead stub of this shape was found.
- **Other dead stub found, not previously on the gap list:** `vendor/companion/src/ChiCompanionPanel.tsx` itself — vendored but dead in `xcamp-demo` (zero imports from `src/`, confirmed by grep). Its only live sibling import, `ComponentRenderer` from the same `@xchange/companion` package, is used by the real `/home` Companion chat (`src/components/companion/ChatThread.tsx:5-6`) — that one import is legitimate and live; the rest of the vendored companion package is not.
- **Transcript extraction — a real backend call built, shipped, then routed around:** `src/lib/transcripts-api.ts`'s `extractTranscript()` makes a real, auth-gated call (`supabase.auth.getSession()` + `fetch` to `xcamp-backend`'s `/api/transcripts/extract`). `src/components/founder/TranscriptOverlay.tsx` (used by Founder Home) does **not** call it — its own header comment explains it was tried, found to throw "You need to be signed in" for every anonymous demo viewer (confirmed: "network tab empty" per the comment), and replaced with a fixture-driven `simulateTranscriptExtraction()`. This is direct, in-repo proof that a real, auth-gated hook cannot be dropped into a `/demo/*` screen unmodified — Epic 3 needs a demo-safe wrapper (fixture fallback when unauthenticated), not a straight port, for any hook in this category.
