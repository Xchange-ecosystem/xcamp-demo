## 1. Phase 0 findings

### 1.1 Routing

The app uses **TanStack Router** (`@tanstack/react-router` + `@tanstack/router-plugin`) with file-based routing: every route is a file under `src/routes/*.tsx` using TanStack's flat dot-segment naming convention (e.g. `demo.founder.dashboard.tsx` → `/demo/founder/dashboard`), not nested folders. `vite.config.ts` runs `TanStackRouterVite({ autoCodeSplitting: true })`, which is what generates `src/routeTree.gen.ts` at dev/build time. That file is **not present in the working tree** and is listed in `.gitignore` (confirmed: `src/routeTree.gen.ts` at `.gitignore:45`) — a prior commit (`6aa40f3`, "stop tracking generated routeTree.gen.ts, let build regenerate it fresh") deliberately untracked it. It was not regenerated or inspected this session, per the standing rule; route resolution below was traced by reading each route file's `createFileRoute()` call directly, not by reading generated output.

The root route (`src/routes/__root.tsx`) mounts `AuthProvider`/`ActiveProjectProvider`/`QueryClientProvider` globally but applies **no route-level auth gate** itself — auth checks, where they exist, live inside individual shells (e.g. the main app's `AppShell`), not centrally.

### 1.2 The demo shell

Confirmed real names: **`DemoShell`** (`src/components/demo/DemoShell.tsx`) and **`DemoNavRail`** (`src/components/demo/DemoNavRail.tsx`). `DemoShell` wraps `Sidepanel`/`RightPanel`/`CompanionRail`/`Sidebar` context providers (kept because some reused child components read them) plus `useAmbientToasts(persona)`, and lays out `DemoNavRail` beside an inset, rounded content card styled entirely with `--skin-*` CSS custom properties. Per its own creation commit (`fbe86b3`, "Fix /demo/* auth redirect and add missing investor route"), `DemoShell` exists specifically to **drop** the main app's `AppShell` auth redirect, which had been incorrectly gating `/demo/*` — the demo is deliberately public/no-login.

`FounderShell` (`src/components/founder/FounderShell.tsx`) is a thin persona-specific wrapper around `DemoShell` for the founder routes only; investor and collaborator routes call `DemoShell` directly.

Nav items per persona, read verbatim from source:

- **Founder** (`FounderShell.tsx`): Home (`/demo/founder`, exact) · Companion (`/demo/founder/companion`) · Navigator (`/demo/founder/navigator`) · Dashboard (`/demo/founder/dashboard`)
- **Investor** (`demo.investor.index.tsx` / `demo.investor.portfolio.tsx`): Portfolio (`/demo/investor`, exact) — **one item**. Comment in source: *"Investor only has one screen today — Navrail gets a single item... More screens... deferred to a later session."*
- **Collaborator** (`demo.collaborator.tsx`): Assignments (`/demo/collaborator`, exact) — **one item**. Same "deferred to a later session" comment.

### 1.3 The three personas

Confirmed: the literal paths `/demo/founder`, `/demo/investor`, `/demo/collaborator` exist exactly as expected, declared in `DemoNavRail.tsx`'s `PERSONAS` array and used by a persona-switcher dropdown in the nav rail. `/demo` itself (`demo.index.tsx`) does a `beforeLoad` redirect to `/demo/founder`. Reality does **not** diverge from the expected three-persona shape — but the *depth* behind two of the three personas is minimal: founder has 4 screens, investor and collaborator have exactly 1 each (with `/demo/investor` and `/demo/investor/portfolio` being two routes rendering the identical `InvestorPortfolioScreen` component).

### 1.4 Design system surface

- **Tokens:** CSS custom properties, `var(--skin-bg)`, `var(--skin-surface)`, `var(--skin-surface2)`, `var(--skin-ink)`, `var(--skin-ink-soft)`, `var(--skin-ink-faint)`, `var(--skin-line)`, `var(--skin-accent)`, `var(--skin-good)`, `var(--skin-bad)`, `var(--skin-radius*)`, etc. — defined as static `:root` / `.dark` blocks in `src/styles.css`, **not** produced by a runtime `applySkin()`/`SkinProvider` from `@xchange/ui`. `useBrand()` (`src/lib/brand.ts`) supplies logo/name only (single-brand "Xcamp," no more Nox/Xcamp split in dark mode).
- **Component library:** shadcn/Radix primitives in `src/components/ui/` (47 files; roughly 29 of them are unused scaffold per an older in-repo audit, not independently re-verified here). `@xchange/ui`, `@xchange/client`, `@xchange/companion` are **not** npm dependencies (absent from `package.json`) — they exist only as vendored source copies under `vendor/{ui,client,companion}/`, and only one file in the whole app (`src/components/companion/ChatThread.tsx`) imports anything from vendored `@xchange/companion`, and that's outside `/demo/*`. Demo screens build entirely on shadcn + hand-rolled `--skin-*`-styled `<div>`s.
- **Prevailing convention in `/demo/*` today:** a fixture-driven `CardFeed<T>` generic list component (`src/components/card-feed/CardFeed.tsx`, documented in `src/components/card-feed/README.md`) used identically across all three personas via per-use-case config objects; rounded (`--skin-radius-lg`) card surfaces; `--skin-accent` teal/emerald accent; shadcn `Button`/`Input`/`Textarea`/`Dialog`/`Sheet` for interactive controls.
- **Reference screens for the design session** (representative of current visual standard):
  1. `src/routes/demo.founder.index.tsx` (Founder Home) — composer + mode pills + mock-processing state + `CardFeed` + `ProposalModal`, the most fully-realized demo screen.
  2. `src/features/investor-portfolio/InvestorPortfolioScreen.tsx` (+ `RankedPortfolioBars.tsx`, `ProjectSelectorStrip.tsx`, `EcosystemMetricsPanel.tsx`) — two-column layout, ranked bars, metrics aside.
  3. `src/features/collaborator/CollaboratorScreen.tsx` (+ `AssignmentFeed.tsx`, `ValueWallet.tsx`, `CollaboratorMetrics.tsx`) — feed + sidebar-metrics pattern.

### 1.5 Data

Confirmed **mix, cleanly separated by app half**:
- Every screen under `/demo/*` reads exclusively from typed local fixtures in `src/fixtures/*.ts` (`people`, `projects`, `objectives`, `tasks`, `metrics`, `portfolio`, `feed`, `transcripts`, `chat`, `wallet`, `assignments`). No `/demo/*` route or component imports `supabase` (confirmed by grep across `src/routes/demo*.tsx`, `src/features/investor-portfolio/`, `src/features/collaborator/`, `src/components/founder/`: zero hits).
- The older, non-demo "main app" (routes like `/home`, `/navigator`, `/journal`, `/notes`, `/profile`, `/project/$projectId`, `/project/$projectId/goals`, `/portfolio`, `/task/$taskId`, `/auth`, plus the sandbox routes) reads **live Supabase** (project `ueebzuleyrnsrxbowdfa`) throughout — confirmed directly in `src/routes/project.$projectId_.goals.tsx` (`supabase.from("projects")...`), `src/lib/navigator-api.ts` (`import { supabase }`), `src/lib/watchlist-api.ts` (RPC calls), and others.
- **`demo_tables.sql` is confirmed still absent** — no such file exists anywhere in `supabase/migrations/` (only three unrelated migrations: storage RLS scoping, a notes date-field addition, and objective-policy grants). This is consistent with the demo intentionally staying fixture-only rather than getting its own backing schema.

## 4. In the demo (or the repo generally) but not on the roadmap

These have no correspondence to any of the 34 roadmap items above:

- **Notes app** (`/notes`, `src/components/NotesBrowser.tsx`) — a full personal/project-linked note manager (search, sort, filters, bulk archive/assign, rich-text editor, AI auto-tagging, an "Organise" launch point). Distinct from Founders' Journal (voice-entry capture) and from Organiser (which it merely calls into).
- **Ambient persona toasts** — `src/hooks/useAmbientToasts.ts` + `src/components/demo/ambientToastPools.ts`, wired into `DemoShell`. Fires 2–4 randomized, non-interactive toast notifications a few seconds after landing on any `/demo/*` page or switching persona, using content pools keyed by persona (founder/investor/collaborator; admin explicitly excluded) built from the same fixtures. In-memory only, no real backing data; toast CTA buttons just dismiss.
- **Recap** — `api/recap/extract.ts` + `api/recap/publish.ts`, two Vercel serverless functions with **no UI or route anywhere** in `src/routes/`. `extract.ts` sends a meeting transcript to an LLM to pull out structured follow-ups without persisting the transcript; `publish.ts` writes reviewed follow-ups to Supabase and sends one personalized email per recipient via SendGrid. Per its own commit message, "No UI: `/admin/recap` and `/recap/:token` are deferred to a later session." Backend-only, unreachable as a screen.
- **`/sandbox/task-panel-v3`** and **`/sandbox/task-panel-live`** — explicitly self-labeled "THROWAWAY SANDBOX — not a real app surface, not linked from any nav," reproducing two different xcamp-foundation task-detail layouts against real dev-tenant data for side-by-side comparison. Only a "done" checkbox actually writes to the DB.
- **`/ai-plan`** — a bare `ComingSoonPage` stub ("AI-generated project planning and roadmapping — coming soon"), unrelated to Template Builder/Backcaster despite similar subject matter.
- **Item relationship graph + AI link suggestions** (`src/components/sidepanel/ItemGraph.tsx`, `ItemSidepanel.tsx`'s `suggestLinks`) — shared cross-app plumbing (a force-directed graph of an item's linked notes/objectives/tasks), not a standalone screen.
- **Task-level Match/Collaborate tab** (`src/components/task-detail/MatchCollaborateTab.tsx`) — an explicit non-persisting placeholder inside the shared task-detail shell, showing a mock collaborator/remuneration table with a disabled "Invite a collaborator" button.
- **Companion Rail / Altitude system** (`src/components/companion/CompanionRail.tsx`) — cross-cutting main-app chrome (zoom-depth "Altitude" toggle, Role/Mood panels, global item search) mounted app-wide; not itself a named roadmap app.
- **Profile → Appearance** (`/profile/appearance`) — theme (light/dark/system) and language settings; a Profile sub-page, included for completeness.

4. **Ecosystem Home Page (item 2) vs. Monitoring & Reporting (item 25):** both resolved to the identical `ecosystem-dashboard.tsx` → `ComingSoonPage` stub. Same question as above — one build target or two?

Unclear whether it was ever built and removed, or was never implemented as originally specced — this repo's history alone can't resolve that; would need `xcamp-companion`/`xcamp-nox-founder-app` history, which was out of scope this session.

## 6. What we did not check

This was a source-only audit; no dev server was started and no browser click-through was performed (Vercel previews are SSO-blocked from this session). Every route→component trace above reflects what the source declares, not confirmed runtime behavior. Specific items that need live verification before being treated as settled:

- Whether each `/demo/founder/*`, `/demo/investor(/portfolio)`, and `/demo/collaborator` screen actually renders without console errors when clicked through in a browser (only static reads were performed).
- Whether the two duplicate investor routes (`/demo/investor` and `/demo/investor/portfolio`) actually behave identically in the browser as their shared component suggests.
- Whether the Collaborator screen's interactive flows (`AssignmentFeed`'s deliver/upload dialogs, `ValueWallet`) work end-to-end when clicked, not just when read.
- Whether the ambient persona toasts actually fire with correct timing/content on a real page load or persona switch (only the scheduling/pool logic was read, not observed).
- What an **unauthenticated** visitor to any "Built (main app only)" route (`/profile`, `/navigator`, `/portfolio`, `/journal`, `/notes`, `/project/$projectId/goals`, etc.) actually sees — whether it redirects to `/auth`, 404s, or partially renders. This audit's "Built (main app only)" classifications assume an authenticated session against the seeded dev tenant; that assumption was not verified live.
- Whether those same live-Supabase screens return non-empty data for the currently seeded dev tenant, or would render empty states, in practice.
- Whether the permanently `disabled` "Marketplace"/"Investor" audience-toggle buttons in `PortfolioView.tsx` are inert as they appear in source, or throw/console-error on click.
- The sandbox routes' claimed requirement of "a signed-in user with RLS access to a specific dev-tenant objective" was read from a code comment, not independently verified against a live session.
- Whether `routeTree.gen.ts`, when actually produced by a real build, resolves to anything beyond what the raw route file names/content imply (this audit deliberately did not run a build, per the standing rule against regenerating it).
- Whether Recap's serverless functions (`api/recap/extract.ts`, `api/recap/publish.ts`) actually deploy and execute correctly on Vercel — only their source was read, not their runtime behavior.
